# ArkOffer reconstruction: evidence and scope

ArkOffer is a working local full-stack reconstruction of the observed Metaview website and selected recruiting workflows. It is **not a 100% functional clone of Metaview**. It has its own React frontend, Express API, SQLite storage, authentication, and optional external-provider adapters. Metaview's private source code, backend services, production datasets, and integration credentials were not obtained.

This record describes the implementation reviewed on **12 October 2026**. [PARITY.md](PARITY.md) maps source products and routes to local behavior and remaining gaps. [The API reference](../server/API.md) documents the actual request contracts and limits.

## What runs locally

React, TypeScript, React Router and Vite serve public and signed-in screens. Express serves authenticated workspace APIs and selected public-token/form routes. SQLite persists `DATA_DIR/arkoffer.sqlite`; source files live under `DATA_DIR/uploads`. The application does not forward requests to Metaview or reuse its authenticated endpoints, tracking scripts or cookies.

Signup creates a personal workspace with 12 editable built-in templates and optional fictional examples. Users can create or join more workspaces. Additive migrations preserve legacy accounts and populate memberships once; removed memberships are not recreated at restart. A session selects one active workspace independently of sessions on other browsers.

Passwords use salted scrypt. Seven-day session cookies are HttpOnly, SameSite=Lax and Secure in production; only token hashes are stored. Public session-management IDs do not expose the cookie token. Mutations require an allowed Origin except provider webhooks with their own signature verification. Workspace settings and management operations enforce roles.

Notes have an owner, private/workspace visibility and optional viewer/editor grants to active teammates. Owners and administrators can read workspace notes. Member access is limited to owned, explicitly shared or workspace-visible conversations, including permissions inherited from shared collections. Permission checks cover lists, direct reads, edits, uploads/downloads, versions, public-link management, comments, assistant sources and exports. Comments are persistent; this is not real-time multi-cursor editing.

The product also supports local candidate/job/application records, CSV imports, manual recruiting decisions, templates, text/choice screening questionnaires, persistent published responses, reports, public intake forms and the public marketing pages described in the parity matrix. New team invitations are seven-day copy links, stored as hashes and accepted once by a matching signed-in email. Possession of a copied invite is a capability; an unverified signup email is not independent proof of mailbox ownership. Invitation emails are not automatically sent.

## AI, retrieval and files

Without a configured text provider and the current workspace ID in its allowlist, notes and Q&A use labeled transcript extraction. A supplied server credential alone does not enable every newly registered workspace. Template synthesis, translation and audio transcription require the allowed provider path. Local extraction respects format/length preferences and preserves source language.

Explicit allowed actions request summaries, translation, transcription or answers from the configured provider and model. Single-conversation generation/Q&A clips source input at 100,000 characters and returns source metadata. Provider errors preserve existing notes; concurrent edits cause a conflict instead of an overwrite. Automated provider-response tests use mocks. A separate isolated synthetic check also exercised the configured live text model through the four reviewed workflows below.

The workspace assistant at `/app/fillmore` keeps per-user, per-workspace threads and citations across accessible, unarchived notes. Local retrieval ranks matching transcript excerpts, taking at most three per conversation and 12 overall, with each excerpt capped at 900 characters. Retrieval streams up to 50 MB of the newest conversation records (at most 2,000 records), matches up to 20 question terms and explains when the scan limit is reached. Selecting a source narrows the search. Optional synthesis receives those excerpts; saved generated answers are capped at 20,000 characters. It does not browse the web, run autonomous actions or decide hiring outcomes. Threads are limited to 100 per user/workspace and 100 questions each. Answers whose cited source text changes or becomes inaccessible are withheld on subsequent reads. This differs from the single-note question panel, whose UI chat state is not persistent.

Uploads accept supported text, VTT, PDF, DOCX, audio and video up to 50 MB; document extraction has a 10 MB input limit. Text/extracted content is capped at 800 KB. PDF extraction supports text-based PDFs up to 200 pages; DOCX bounds expanded data at 20 MB, XML parts at 4 MB and entries at 1,000. Extraction uses workers with a ten-second deadline and at most two concurrent jobs. There is no OCR. Corrupt, empty, encrypted/unsupported or oversized documents return explicit errors and failed uploads do not create notes. Optional audio transcription has a separate 25 MB provider limit. Uploaded media supports authorized byte-range playback, but not synchronized word timing or video clipping.

Published screening links use immutable question snapshots and hashed random tokens. Each seven-day link accepts one validated candidate response; an identical retry is idempotent. Authorized users can review responses; publication management is role-restricted. Public reads do not expose submitted identities or answers. Optional spoken prompts and recorded answers are supported. Audio is converted to bounded mono 16 kHz PCM, transcribed on explicit consent, then reviewed/corrected before submission. The server links original transcripts, duration and corrections to the published question. A configured text provider can supply one neutral clarification. This is a turn-based interview, with no retained raw recording, real-time voice/video agent or automated evaluation.

## Reviewed AI workflows

Job drafting, application evidence review, report extraction and note-edit drafts share the existing `createAi` adapter, configured model and text-workspace allowlist. They introduce no environment keys, provider accounts or database service. Requests are bounded and do not automatically retry paid generation. Their drafts and results live in author/workspace-scoped tables, outside generic resource JSON and public conversation shares. Manual workflows remain available when text AI is disabled; these new AI operations do not pretend that extraction is a generated result.

**Job descriptions:** `/app/job-posts` offers a private draft from an explicit role brief, company context and tone, either for a new job or a current job revision. The result separates the proposed description, editorial suggestions and missing details. A reviewer can edit the description and must confirm before applying it to a workspace job. New jobs start as drafts; existing status and metadata are preserved. Session/workspace identity and the original job content are rechecked after generation and before apply. Repeated application returns the current job without overwriting later edits. Limits include 100 retained drafts per author/workspace, two active drafts and 30 requests per workspace/hour. This does not publish to external job boards, write to an ATS or establish legal compliance.

**Application evidence:** `/app/applications` supports up to ten explicitly approved criteria per job, entered manually or drafted from a job description. Approved criteria are shared with the workspace; AI criteria drafts, analysis history and reviewer notes remain private. After explicit consent, analysis uses only the linked candidate's role/company/skills and up to five selected accessible transcripts, with a combined 60,000-character source limit. Every criterion receives checked source quotations where available, missing information and a neutral follow-up question. Reviewers save their own notes and reviewed state; existing manual stage and hiring-decision controls remain separate. Changes to the application, candidate, job, approved criteria, selected evidence or access make prior results stale and hide their contents. Limits include ten requests per user/hour, 50 per workspace/hour, two active requests per workspace, a 55-second cancellation deadline and a 20 KB provider-output limit. No CV ingestion, applicant ranking/scoring, automated rejection, ATS stage mutation or continuous review is implemented.

**Report views:** `/app/reports` retains its local aggregate charts and adds private saved extraction views. The author chooses a question, up to 20 accessible conversations, title/date filters and up to five typed columns (`text`, `number`, `boolean`, `currency`). This is a manual view builder with AI cell extraction; it does not turn natural language into a complete report definition. A consent-confirmed run queues at most 100 cells and exposes progress, cancellation, evidence, human annotations and CSV export. Nonempty values require exact transcript quotations; unsupported or ambiguous answers are marked not documented. Each transcript is clipped to 60,000 characters with an explicit truncation indicator. Source text and permission are rechecked during processing and when results, annotations or CSV are read; unavailable source rows disclose no saved values. Limits include 100 views per author/workspace, one active run per author/workspace, 500 cells per user and 2,000 per workspace over 24 hours, and bounded output. A one-second server worker processes stored queued runs; interrupted processing is marked rather than automatically retried. There are no report subscriptions, scheduled report emails or shared report-result permissions.

**Note edits:** `/notes/:id` offers private per-section/TLDR drafts to shorten, expand from evidence, reformat as bullets/paragraphs or follow custom instructions. Explicit user-supplied pronoun wording is optional; names, gender and pronouns must not be inferred. Source quotations and before/after previews precede a separate Apply action; drafts can be discarded or reopened from history. A source fingerprint covers the complete original conversation and its saved versions. Apply rechecks it and atomically saves the previous version, updates only the selected content and marks the draft applied. Later edits survive repeated apply. Limits include 20 drafts per user/workspace per ten-minute window, the latest 100 drafts per author/conversation, 100 conversation versions, 30,000 characters of target text, 60,000 transcript characters for AI edits, a 45-second provider deadline and the 1 MB conversation cap. Exact case-sensitive replacement/redaction needs no AI and has an explicit scope: selected content, all current section contents plus TLDR, or those fields plus transcript. It leaves titles, candidate metadata, snippets, retained versions/drafts, exports and other records unchanged; it is not complete data erasure.

Dedicated API and browser suites for these workflows use synthetic evidence and mocked AI responses or the provider-free replacement path. They check persistence, private ownership, source freshness, consent/application boundaries and provider failures. Final execution results belong in the delivery PR. A separate bounded synthetic live-model check completed job draft/apply, note preview/apply/version, exact application evidence review with unchanged manual status, and queued typed report extraction/CSV. One application request first failed with a provider/transport error before a controlled rerun succeeded; this check does not establish continuous reliability or general hiring quality.

## Provider configuration

Start from [.env.example](../.env.example), supply credentials in a private server environment, and restart. Do not commit credentials, tokens or real workspace IDs. Authenticated `GET /api/workspaces` returns the user's workspace IDs. `LLM_WORKSPACE_IDS`, `OPENAI_WORKSPACE_IDS`, `ENRICHMENT_WORKSPACE_IDS`, `SLACK_WORKSPACE_IDS`, `PROVIDER_WORKSPACE_IDS`, `MAIL_WORKSPACE_IDS` and `BILLING_WORKSPACE_IDS` are separate comma-separated allowlists; blanks enable no workspace for their funded services. Provider operations that manage external state also require their application roles and explicit UI action.

### Text gateway and voice screening

RoboApply-style text settings are supported: `LLM_PROVIDER=openrouter`, `OPENROUTER_API_KEY`, `OPENROUTER_BASE_URL` (or higher-priority `OPENROUTER_API_BASE_URL`), `LLM_MODEL`, and `LLM_WORKSPACE_IDS`. The base is an exact HTTPS API prefix; `/chat/completions` is appended. Model names are preserved exactly. `LLM_INTERVIEW_MODEL` falls back to `LLM_MODEL`; `LLM_INTERVIEW_REASONING_EFFORT` is optional. Direct OpenAI uses `OPENAI_API_KEY`, optional `OPENAI_BASE_URL`, and `OPENAI_MODEL`; `OPENAI_WORKSPACE_IDS` remains the legacy allowlist fallback when `LLM_WORKSPACE_IDS` is absent; an explicitly empty `LLM_WORKSPACE_IDS` disables text AI. Empty allowlists permit no funded workspaces. Requests do not retry automatically or follow redirects with credentials. Reference: [OpenRouter request format](https://openrouter.ai/docs/api/reference/overview).

Voice screening separately requires `OPENAI_API_KEY`, `OPENAI_WORKSPACE_IDS`, and optional `OPENAI_TRANSCRIPTION_MODEL` (voice default `gpt-4o-mini-transcribe`; existing uploaded-note transcription default `whisper-1`). An explicit `OPENAI_TRANSCRIPTION_BASE_URL` can select a compatible voice endpoint; text gateway configuration never implicitly enables audio. Browser speech synthesis reads prompts using installed voices; availability and language quality depend on the browser. Microphone permission and transcription consent are explicit. Each answer is at most two minutes, verified from WAV bytes, with three attempts per question and a workspace hourly cap. Written answers remain available. No raw recording is persisted. Abandoned draft transcripts on expired/revoked links are cleared opportunistically on subsequent voice uploads; this is not a background retention guarantee.

The copied application environment may include unrelated `DATABASE_URL`, `APP_URL`, or `PUBLIC_APP_URL` values. ArkOffer continues to use its SQLite `DATA_DIR`; it does not connect to the other application's database. Set ArkOffer-specific exact origins for each enabled integration. Never reuse another application's OAuth callback or production mail origin accidentally.

### Candidate enrichment

Set `PDL_API_KEY` and `ENRICHMENT_WORKSPACE_IDS`. A workspace admin explicitly authorizes a paid lookup from a professional profile, work email, or name/company identity. The fixed People Data Labs person endpoint returns a restricted professional-field allowlist. ArkOffer retains safe proposal fields and source provenance, not raw provider payloads, personal phones or home addresses. The user selects fields to apply; version and identity checks protect concurrent/manual edits. Request UUIDs persist retries; uncertain outcomes require a new explicitly approved attempt. No-match, provider failure and configuration absence are distinct states. Reference: [People Data Labs person enrichment](https://docs.peopledatalabs.com/docs/person-enrichment-api).

### Slack

Create a Slack app with `commands`, `chat:write`, and `im:write` bot scopes. Configure OAuth redirect `<SLACK_APP_ORIGIN>/api/slack/callback`, slash command `/arkoffer` request URL `<SLACK_APP_ORIGIN>/api/slack/commands`, and the optional signed event URL `<SLACK_APP_ORIGIN>/api/slack/events`. Set the app ID/client ID/client secret/signing secret, a stable 64-hex `SLACK_ENCRYPTION_KEY`, explicit ArkOffer `SLACK_APP_ORIGIN`, internal `SLACK_WORKSPACE_IDS`, and permitted external `SLACK_TEAM_IDS`. Slack requires a publicly reachable HTTPS endpoint for live callbacks; localhost configuration alone cannot receive them.

An owner/admin installs the app. Each member generates a short-lived link code in Settings and submits `/arkoffer link CODE`; email similarity never links identities. `/arkoffer ask QUESTION` answers privately using the same evidence-limited engine as ArkOffer. Every model input source is retained in a proof and checked against fresh membership, access, title and exact transcript text before display, approval and sending. OAuth tokens are encrypted, request signatures/timestamps/replays verified, and receipts acknowledged before provider work.

Personal digest/reminder schedules are opt-in and default to drafts requiring approval. Persistent jobs expose failures and unknown delivery outcomes; ambiguous sends are not blindly retried. Disconnect/unlink cancels pending work. This does not read Slack history, post to public channels, contact candidates, autonomously change recruiting records, book meetings, support enterprise installs or rotate OAuth tokens. The single-process worker runs only while ArkOffer runs. References: [Slack OAuth](https://docs.slack.dev/authentication/installing-with-oauth/), [signed requests](https://docs.slack.dev/authentication/verifying-requests-from-slack/).

### Calendar OAuth

Set `CALENDAR_TOKEN_ENCRYPTION_KEY` to a securely generated, stable 64-character hexadecimal secret, for example by generating one with `openssl rand -hex 32`. Back it up separately. Set `CALENDAR_APP_ORIGIN` to an exact origin in `APP_ORIGIN`; production requires HTTPS, while localhost HTTP is accepted for development.

For Google, configure `GOOGLE_CALENDAR_CLIENT_ID` and `GOOGLE_CALENDAR_CLIENT_SECRET` with the exact callback `<origin>/api/calendar/google/callback`. For Microsoft, configure `MICROSOFT_CALENDAR_CLIENT_ID` and `MICROSOFT_CALENDAR_CLIENT_SECRET` with `<origin>/api/calendar/microsoft/callback`. Each user connects through Settings and provider consent. OAuth state is expiring, session-bound and single-use; PKCE is used. Tokens are encrypted with AES-256-GCM and bound to the user, workspace and provider.

Sync is explicit, for the connected primary calendar and next 30 days, capped at 1,000 events. Imports are duplicate-safe, preserve local note edits and archive observed cancelled events. Disconnect removes local credentials while retaining imported notes. There is no background webhook/delta sync, shared-calendar picker, calendar write-back or automatic meeting-bot attendance rule.

References: [Google web-server OAuth](https://developers.google.com/identity/protocols/oauth2/web-server), [Google events.list](https://developers.google.com/workspace/calendar/api/v3/reference/events/list), [Microsoft authorization code flow](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow), [Microsoft calendarView](https://learn.microsoft.com/en-us/graph/api/calendar-list-calendarview?view=graph-rest-1.0).

### Greenhouse Harvest v3

Set `GREENHOUSE_CLIENT_ID`, `GREENHOUSE_CLIENT_SECRET` and `PROVIDER_WORKSPACE_IDS`. `GREENHOUSE_USER_ID` optionally supplies a numeric provider user scope. A workspace owner/admin can run a manual import from Settings.

The adapter uses client credentials and fixed Harvest v3 endpoints. It imports nonprivate candidates, nonconfidential jobs and associated applications; it preserves local edits while updating separate provider metadata. Responses are bounded, with at most ten pages and 1,000 records per resource. Exceeding those bounds fails the import rather than silently importing a partial catalog. There is no continuous synchronization, attachments/CV import, scorecard write-back or remote stage mutation.

References: [Authentication](https://harvestdocs.greenhouse.io/docs/authentication), [pagination](https://harvestdocs.greenhouse.io/docs/pagination), [candidates](https://harvestdocs.greenhouse.io/reference/get_v3-candidates), [jobs](https://harvestdocs.greenhouse.io/reference/get_v3-jobs), [applications](https://harvestdocs.greenhouse.io/reference/get_v3-applications).

### Recall meeting capture

Set `RECALL_API_KEY`, `PROVIDER_WORKSPACE_IDS`, and `RECALL_REGION` to one of `us-east-1`, `us-west-2`, `eu-central-1` or `ap-northeast-1`. The UI requires a supported meeting URL and explicit recording-consent acknowledgment before requesting a bot. Scheduled joins must be between ten minutes and 30 days ahead.

Users explicitly refresh status, leave a call, cancel supported scheduled capture or import a ready transcript. Creation request identities prevent accidental duplicate local requests; ambiguous provider outcomes require recovery rather than blind automatic retries. Imported notes are private to their creator subject to workspace administration. Transcript imports are bounded to 20,000 provider segments, an 8 MB response and 500,000 characters. The adapter does not import a local media recording, receive signed status webhooks, automatically follow calendars or reproduce the source meeting infrastructure.

References: [Create bot](https://docs.recall.ai/reference/bot_create), [retrieve bot](https://docs.recall.ai/reference/bot_retrieve), [leave call](https://docs.recall.ai/reference/bot_leave_call_create), [delete bot](https://docs.recall.ai/reference/bot_destroy), [transcription](https://docs.recall.ai/docs/recallai-transcription), [download schemas](https://docs.recall.ai/docs/download-schemas), [regions](https://docs.recall.ai/docs/regions).

### Resend and account mail

Default `MAIL_MODE=outbox` saves sequence messages locally and makes no mail-provider call. Live sending requires `MAIL_MODE=resend`, `RESEND_API_KEY`, a verified `MAIL_FROM`, HTTPS `PUBLIC_APP_URL` and `MAIL_WORKSPACE_IDS`; `MAIL_REPLY_TO` is optional.

A sequence owner/admin previews personalized recipients and approves a revision before activation. Persistent messages retain the approved snapshot, delays and per-message idempotency keys. Pause/resume/cancel, manual reply status, unsubscribe links and workspace suppression lists are implemented. The server worker handles bounded retries for explicit transient failures, polls known provider statuses and stops on unknown delivery outcomes. It runs only while the server is running; this is not mailbox OAuth, automatic inbound-reply detection or a delivery guarantee. Limits include ten steps, 100 recipients per activation and 1,000 active/paused enrollments per workspace.

Account password changes work without mail and require the current password. They rotate this session and revoke others. Reset links require live mail, expire after 30 minutes, are hashed and single-use, and invalidate all sessions when consumed. Verification links require a matching signed-in account and expire after 24 hours. Account tokens never enter sequence outboxes or API responses. Forgot-password responses are generic and acknowledged before mail-provider I/O; shutdown drains pending requests. A process crash can interrupt delivery, so the receipt does not assert successful delivery.

References: [Send email](https://resend.com/docs/api-reference/emails/send-email), [idempotency keys](https://resend.com/docs/dashboard/emails/idempotency-keys).

### Stripe billing

Set `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, at least one recurring seat price (`STRIPE_PRICE_TEAM` / `STRIPE_PRICE_BUSINESS`), HTTPS `PUBLIC_APP_URL` and `BILLING_WORKSPACE_IDS`. Use Stripe test mode first. Settings displays configured provider prices and test/live mode; an owner/admin chooses a plan and seat quantity before redirecting to Checkout.

Register the snapshot webhook endpoint `<PUBLIC_APP_URL>/api/billing/webhook` for subscription created/updated/deleted and checkout completion events. Raw request bodies are verified against the signing secret with a five-minute timestamp tolerance. Stored customer/workspace bindings, replay checks and stale-event handling protect updates; refresh reconciles provider status. Customer-portal access and checkout cancellation/recovery are available.

This tracks commercial state; it does not yet enforce subscription features, source-product usage credits, metering or paid-seat quotas on invitations. Public pricing-page figures remain illustrative. No real charge or live subscription was created during repository validation. Reference: [Stripe webhook signature verification](https://docs.stripe.com/webhooks#verify-manually).

## Remaining implementation and operational work

The working adapters do not establish complete source parity. Missing features include broad external candidate discovery/verified contact discovery; Gmail/Outlook inbox integration and automatic reply detection; real-time voice/video screening agents; CV ingestion, AI applicant ranking and automated ATS rejection; ATS write-back and providers beyond Greenhouse; external job publishing; real-time coediting and video snippets; natural-language automatic report construction, subscriptions and scheduled report delivery; autonomous Slack recruiting actions and meeting booking; enterprise SSO/MFA/SCIM, managed domains and retention policies; and enforced usage/credit entitlements.

No production deployment, operational monitoring or load test is included. Live verification is limited to the bounded synthetic text-model workflows above; other provider integrations and physical microphone capture remain unverified. This is a single-process SQLite/local-files installation. Backups, encryption-key handling, HTTPS, abuse controls, recovery operations and legal policies need an operating environment and operator decisions. Configuration alone does not establish a successful external connection.

## Public content and asset provenance

The homepage follows the observed visual structure: announcement strip, white navigation, rounded calls to action, split hero, product selector, feature accordions, resource cards, and footer. ArkOffer replaces the source brand and uses original educational articles and company copy. It does not claim Metaview's customers, funding, certifications, hiring openings, or testimonials.

The hero image and fonts downloaded from observed public asset URLs are recorded with origins and hashes in [origins.json](../public/marketing/origins.json). Public availability is not a license grant. Their ownership and use rights must be resolved for distribution or replaced with licensed assets. The legal pages are explicitly draft ArkOffer documents, not copied Metaview policies or finalized advice.

## Validation evidence and boundaries

Reproduce the repository checks with:

```sh
npm test
npm run build
npm run test:e2e
npm run format:check
```

The API suites in [tests/server](../tests/server) exercise authentication, migrations, memberships/roles, conversation permissions, sharing, source files, versioning, document limits, screening responses, account security, provider request boundaries and error handling. The `job-drafts`, `application-review`, `report-views` and `note-editing` suites add private drafts/results, explicit review and consent, stale-source handling, quotas, idempotency and failure preservation. Calendar, mail, ATS, meeting, billing and AI tests use injected responses. Browser suites in [tests/e2e](../tests/e2e) cover local browser-to-API persistence, cross-session account changes, invitations/workspace switching and recruiting flows, including the four reviewed AI workflows.

Final combined-suite counts and remote checks belong in the delivery PR after execution. Earlier marketing review covered 19 public routes, desktop/390-pixel layouts, navigation, local forms, search and pricing controls. The microphone regression simulates a late permission result; it does not establish physical recording. Screenshots support layout review, not pixel equality of every source state.

The GitHub workflow runs API tests, production build and Chromium tests. A workflow file is not itself a successful check. Mock-based tests do not establish live provider accounts. The bounded live text-model check does not establish the other integrations, original-service behavior, production capacity, accessibility conformance, hiring quality or 100% source equivalence.
